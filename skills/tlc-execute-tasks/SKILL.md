# Execute Feature Tasks

Main agent is the orchestrator: sets up an isolated run branch, filters pending tasks, groups them into waves, and directly spawns one executor per task within each wave — each executor working in its own isolated worktree off the run branch — via the Agent tool, never delegating coordination to another skill. Respects wave dependencies (wave N finishes before wave N+1 starts), applies approved task diffs onto the run branch in task order, and syncs taskmaster status after each wave. The user decides how failures are handled.

## Steps

| #   | Step                     | Action                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Output / Gate                                                                                                                                                                                   |
| --- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Setup run branch         | `git status --porcelain` — dirty tree → abort. Record original HEAD; `git switch -c <head-branch>-{TAG}` from it                                                                                                                                                                                                                                                                                                                                                                                                                         | Dirty tree → report, stop. Otherwise run branch created and checked out                                                                                                                         |
| 2   | Validate tag & load spec | Confirm `.specs/features/{TAG}/design.md`, `.specs/features/{TAG}/spec.md`, `.taskmaster/execution/metadata.json` all exist; read all 3 in parallel                                                                                                                                                                                                                                                                                                                                                                                      | Missing file → report exact paths, delete run branch, stop. Otherwise extract: design (architecture/complexity/scope), spec (problem/goals/requirements), metadata (waves/critical path/effort) |
| 3   | Fetch pending tasks      | `mcp__mcp-manager__call_tool({server:"taskmaster-ai", tool_name:"get_tasks", arguments:{projectRoot, tag}})`; filter `status != "done"`; sort by `metadata.wave` + dependency graph                                                                                                                                                                                                                                                                                                                                                      | Ordered list of pending tasks                                                                                                                                                                   |
| 4   | Display plan             | Show tag, pending count, effort estimate, execution sequence T0→Tn                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Ask user "Ready to execute {N} tasks? [yes/no]" via AskUserQuestion — no → abort, delete run branch                                                                                             |
| 4.5 | Build wave groups        | Group tasks by `metadata.wave` (no wave metadata → wave 0 / sequential). PARALLEL = 2+ tasks in wave; SEQUENTIAL = 1 task or no wave metadata or all sequential                                                                                                                                                                                                                                                                                                                                                                          | Show wave breakdown, e.g. `Wave 0 (PARALLEL): T0, T1 — 2 tasks`                                                                                                                                 |
| 5   | Execute by wave          | PARALLEL (2+ tasks in wave): batch ≤3 concurrent; each task gets its own executor in an isolated `git worktree` branched off the run branch (see `references/orchestrator-model.md`, `references/agent-prompts.md`). SEQUENTIAL (1 task, no wave, or all sequential): each task still gets its own worktree executor, run one at a time — no inline execution by main agent. Wait for all of wave N before starting N+1. Use `TaskCreate`/`TaskGet`/`TaskList`/`TaskUpdate` to track wave/task progress alongside taskmaster MCP updates | Per-task status: Complete/Blocked/Partial + diff produced + gate result                                                                                                                         |
| 6   | Apply approved diffs     | For each approved task, in task order, `git apply` its diff onto the run branch; conflicts → hand off to `resolve-merge-conflicts` skill                                                                                                                                                                                                                                                                                                                                                                                                 | Run branch updated in task order; conflicts resolved before continuing                                                                                                                          |
| 7   | Clean up worktrees       | `git worktree remove` + delete the task branch for every executor, success or failure — never `rm -rf` on a worktree                                                                                                                                                                                                                                                                                                                                                                                                                     | No stray worktrees or branches left behind                                                                                                                                                      |
| 8   | Sync taskmaster status   | After each wave completes, call `set_task_status` per task with **`tag` required** (omitting it silently no-ops)                                                                                                                                                                                                                                                                                                                                                                                                                         | done / cancelled / deferred / blocked synced incrementally, not batched at the end                                                                                                              |
| 9   | Merge back               | Merge run branch (`--no-ff`) into the original HEAD; leave the result staged/uncommitted for user review                                                                                                                                                                                                                                                                                                                                                                                                                                 | User does the final commit/push — never commit or push on the user's behalf                                                                                                                     |
| 9.5 | Verify completed work    | Main agent inline-runs the `tlc-spec-driven` verify phase against the merged result on original HEAD (author != verifier — main agent did not implement the tasks, so it qualifies), checking each completed task's verification criteria from the spec                                                                                                                                                                                                                                                                                  | Verify pass → proceed to summary. Verify fail on any task → ask user **Retry / Skip / Abort** (same flow as wave failures, see `references/orchestrator-model.md`)                              |
| 10  | Compile summary          | Report per-wave results + completed/skipped/failed counts + merge outcome + verify outcome, hand next step to user                                                                                                                                                                                                                                                                                                                                                                                                                       | See `references/examples.md` for full output format                                                                                                                                             |

## Failure handling

On any task failure in wave N, ask the user **Retry / Skip / Abort** — see `references/orchestrator-model.md` for the full decision flow and status-mapping table. The post-merge verify gate (step 9.5) uses the same Retry/Skip/Abort flow.
